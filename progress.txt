RESEARCH (via document-specialist agent, before authoring Product.wxs's core content): confirmed
exact WiX v5 syntax for Package/MajorUpgrade/StandardDirectory/Feature/Component/ServiceControl/
Environment/Property/Launch, and NSSM's exact command-line quoting rules. Key findings that changed
the plan's assumptions:
- ServiceControl (Stop="both" Remove="uninstall" Wait="yes") DOES work to stop/remove a service by
  name even though NSSM (not WiX's own ServiceInstall) originally registered it — confirmed via the
  MSI ServiceControl table's own Microsoft docs ("This column can be used to control a service that
  is not installed [by this package]").
- Deferred CustomActions calling nssm.exe should use the official WixQuietExec pattern from
  WixToolset.Util.wixext (immediate SetProperty with the SAME Id as the deferred CustomAction —
  Windows Installer copies that property's value into CustomActionData automatically), not a raw
  hand-rolled ExeCommand — requires adding `-ext WixToolset.Util.wixext` to the wix build invocation.
- Port range validation (1024-65535) needs NO custom action at all — WiX's <Launch Condition="...">
  numeric comparison auto-coerces a Property's string value against integer literals for
  >/</>=/<= operators. Simpler than the plan assumed.
- MajorUpgrade Schedule="afterInstallExecute" is the standard choice for "install on top, remove
  what's gone in one transaction"; combined with ServiceControl Wait="yes" this avoids file-in-use
  reboot prompts regardless of schedule choice, since that's governed by RestartManager/file-in-use
  detection, not MajorUpgrade's Schedule value itself.
- <Files Include="...\**"> (WiX v5's glob-harvesting element) generates one Component per matched
  file, preserves subdirectory structure, and is explicitly designed for exactly this use case
  (harvesting a huge vendored tree without hand-authoring hundreds of <File> elements) — confirmed
  via a second targeted research pass.

[REAL CI RUN #1 - PARTIAL FAILURE, FIXED] User triggered the dry-run build-msi job for real on
windows-latest. Task 3's stage-binaries.ps1 worked PERFECTLY first try: checksum-verified and
renamed all 3 binaries correctly, zero issues — the first genuinely-confirmed-working piece of this
whole installer. wix build itself then failed: `error WIX0144: The extension
'WixToolset.Util.wixext' could not be found.`

ROOT CAUSE (confirmed via research, not guessed): `wix extension add WixToolset.Util.wixext/5.0.2`
(no --global flag) caches the extension under a `.wix\extensions\` folder rooted at the CURRENT
WORKING DIRECTORY at the moment `add` ran — the CI step ran from the repo root. build.ps1 then does
`Push-Location installer/windows/` before running `wix build`, a DIFFERENT directory — and WiX does
NOT walk up parent directories looking for a local extension cache the way git/npm/dotnet-tool
manifests do (confirmed: an upstream GitHub issue with this exact repro shape was closed "not
planned" — this is intentional design, not a bug FireGiant will fix). Fixed: added `--global`/`-g`
to both the CI workflow's extension-add step and the README's local-build instructions — a global
add caches under %USERPROFILE%\.wix\extensions\, independent of cwd, which the docs confirm is
checked regardless of which directory `wix build` runs from.

LEARNING: the earlier local verification claim ("ran `wix extension add` for real on macOS, confirmed
via `wix extension list`") was almost certainly subject to this exact same scoping gap — that add
very likely ran from the repo root too, so it never actually proved build.ps1's own `wix build`
(which cd's into installer/windows/) could find the extension. A "the command succeeded" check is
not the same as "the thing that needs it later can actually see it." Real CI is what caught this.

[REAL CI RUN #2 - 3 MORE COMPILER BUGS FOUND+FIXED] After the --global extension fix, wix build got
further and produced real compiler diagnostics (not extension-resolution noise) — genuinely useful
signal:
1. WIX0230: PathEnvComponent used Guid="*" (auto-generated) combined with Component-level
   KeyPath="yes" (directory-as-keypath, the standard idiom for an env-var-only component with no
   file to key off). WiX rejects "*" for this specific pattern — no deterministic per-file identity
   to derive a stable Guid from. Fixed: assigned a fixed, explicit Guid
   (886FFD9F-6BF1-4B67-95C0-C441CC64AF78) that must never change once shipped, same rule as the
   Package's own UpgradeCode.
2. WIX0005 (x6): all 3 services' SetProperty+CustomAction pairs were nested INSIDE their <Feature>
   element as children — invalid per WiX schema (Feature does not accept SetProperty/CustomAction as
   children). This was a real authoring mistake — the CheckPrereqs pair (Task 7) was already correctly
   placed as a Package-level sibling, but the 3 original service pairs (authored earlier, before that
   convention was even established) were not. Fixed: moved all 3 pairs out of their Feature blocks to
   be Package-level siblings, immediately after each Feature's closing tag.
3. WIX0006 + WIX1006 (x3): PREREQ_CLAUDE_FLAG/CODEX/COPILOT were declared as
   `<Property Id="..." Value="" />` — WiX rejects an explicit empty-string Value outright. Fixed by
   removing the Property declarations entirely: a property doesn't need pre-declaring for a
   [PROPNAME] token to resolve (to empty, when never set) in a Formatted string, and the conditioned
   SetProperty actions already handle the "set when selected" half.

LEARNING: none of these 4 bug classes were caught by python3's `xml.etree.ElementTree` well-
formedness check throughout this whole Ralph run — that check only validates the file IS valid XML
(tags balanced, well-nested), not that it's valid PER THE WIX SCHEMA (correct element nesting rules,
attribute value constraints, semantic Guid requirements). "XML well-formed" was never a substitute
for "WiX build succeeds" — it just was the only mechanical check available from a macOS session with
no working wix build. Real CI is doing exactly the job it was always going to need to do.

[REAL CI RUN #3 - LINKER ERROR FOUND+FIXED] After fixing the 4 compiler-level errors (run #2), wix
build progressed to the LINKER stage and hit a new class of bug: WIX0094 "The identifier
'WixAction:InstallExecuteSequence/PREREQ_CODEX_FLAG' could not be found" (and the same for
PREREQ_COPILOT_FLAG).

ROOT CAUSE (confirmed via research, not guessed): a <SetProperty>'s actual SCHEDULED ACTION NAME
defaults to "Set" + Id, NOT the bare Id — this is separate from the Property being set (which IS
named by the bare Id). My PREREQ_CLAUDE_FLAG/CODEX/COPILOT ordering chain (added as a "hardening"
during the earlier architect re-verification) used Before="PREREQ_CODEX_FLAG" etc, referencing the
bare Id — but since nothing ever set Action="PREREQ_CODEX_FLAG" explicitly, the actual registered
action name was "SetPREREQ_CODEX_FLAG", and the bare-Id reference resolved to nothing. A third,
identical latent break existed in CheckPrereqs's own `After="PREREQ_COPILOT_FLAG"` — masked from the
build log by linker de-duplication of repeated references to the same missing symbol; would have
resurfaced on the very next build if only the 2 reported errors had been patched.

Also confirmed WHY the 3 service-registration SetProperty/CustomAction pairs (and CheckPrereqs's own
Before="CheckPrereqs") never hit this bug: their Before/After values target a CustomAction's LITERAL
Id (e.g. "InstallClaudeService"), which has its own explicit <Custom Action="..."> entry in
InstallExecuteSequence and is unambiguous precisely because it differs from that SetProperty's own
"Set"-prefixed default name — no naming collision, no defect.

Fixed: added `Action="<same as Id>"` to all 3 PREREQ_*_FLAG SetProperty elements, overriding the
default "Set"+Id action name to match the bare Id already used everywhere in the Before/After chain
— smaller, more consistent diff than renaming every reference to "SetPREREQ_...".

LEARNING: WiX's compile stage and link stage catch genuinely different bug classes — compile-stage
errors (schema/attribute violations, run #2) do NOT guarantee link-stage correctness (symbol/action-
name resolution, run #3). Each real CI round has surfaced a new, distinct class of previously-
undetectable error. This is expected and exactly why real Windows/CI verification was always the
plan's stated bottom line, not a formality.
